## Beslutning

All styling bruker ren **HTML + CSS** med `ix-`-prefix på alle klasser og custom properties.

### Tokens som CSS custom properties

`--ix-color-primary`, `--ix-spacing-md` etc. Alle tokenverdier er tilgjengelige direkte i CSS uten ekstra byggesteg for konsumenter.

### Utility-klasser

Inspirert av ok-css (SpareBank 1s interne CSS-rammeverk), Tailwind og nettbanken: `ix-m-md`, `ix-flex`, `ix-gap-sm`. Dekker ~80% av behovene. For avanserte behov bruker man egne CSS-filer med design tokens.

Responsive varianter følger mønsteret `ix-{breakpoint}-{klasse}`, f.eks. `ix-sm-flex` for flex fra 768px og oppover. Breakpoints: sm (768px), md (1024px), lg (1280px), xl (1600px).

### Nettleserstøtte

<Term>PostCSS</Term> med `postcss-preset-env` og `autoprefixer` håndterer moderne CSS-syntaks ned til nettleserne i `.browserslistrc`. CSS leveres ferdig kompilert i pakken — konsumenter trenger ikke kjøre PostCSS selv.

### CSS-struktur

`indeks-css/css/`: reset.css, components/, icons/, layout/, surface/, typography/.

Bundelen lastes i rekkefølgen tokens → reset og komponenter → utils. Utilities lastes sist, så de kan overstyre komponentene. På CDN er `index.css` bare en liste med imports (tokens, `components.css`, utils). Grunnen er at en `@import` etter vanlige regler ignoreres av nettleseren.

### Selektorer og spesifisitet

Komponentene skal vinne over vertens elementregler, som `a {}` og `h2 {}` i Docusaurus, uten lapper. Utility-klasser skal fortsatt kunne overstyre ytterste element i en komponent. Det får vi ved at hver del har én hook, og ingen ting pakkes i `:where()`.

1. **Blokk** er klassen `.ix-x`. Finnes det en web component, skrives begge: `:is(ix-x, .ix-x)`.
2. **Én hook per del, aldri to.**
   - Et entydig native barn, eller eneste type barn i en container, styles direkte: `label`, `input`, `summary`, `td`, `> *`.
   - En generisk del får BEM-elementklasse: `.ix-x__del`.
   - Unntak: deler i skjemagruppene som web componenten leser fra markupen, bruker `[data-field='…']`.
3. **Tilstand og varianter** ligger i `data-*`, `aria-*` og pseudoklasser. Aldri BEM-modifier (`--`).
4. **Ingen overflødige kvalifikatorer.** `input` inni `.ix-checkbox` er `input`, ikke `input[type='checkbox']`.
5. **Kombinatorer bare der tilstanden bor på et annet element**: søsken (`input:checked + label`) eller en gruppe rundt (`.ix-checkbox-group[data-state='error'] …`).
6. **Tilstander overstyrer ved å telle betingelser.** Alle tilstandsregler for en del har samme grunnform, og hver betingelse legger på ett ledd. Ved likt antall avgjør kilderekkefølgen: passiv, hover, active, selected, selected hover/active, read-only, error.
7. **Ingen `:where()`**, bortsett fra i `reset.css`, som skal tape mot alt. `:is()` er greit for selektorlister.
8. **Ingen `:has()`**, fordi gulvet i `.browserslistrc` ikke støtter det.

En utility-klasse (`0,1,0`) på ytterste element vinner på rekkefølgen, fordi utils lastes sist. Unntaket er der en variant eller tilstand med vilje setter samme egenskap, som plassen til chevronen i `.ix-card[data-clickable]`.

```css
/* Del med to hooks blir én */
:where(.ix-checkbox) input[type='checkbox']:checked + label,
:where(.ix-checkbox__input:checked) + :where(.ix-checkbox__label) { … }   /* før */
.ix-checkbox input:checked + label { … }                                    /* etter */

/* Modifier blir dataattributt */
:where(.ix-card--clickable:hover) { … }    /* før */
.ix-card[data-clickable]:hover { … }        /* etter */

/* Gruppetilstand over intern tilstand: samme grunnform, read-only står sist */
:is(ix-radio-group, .ix-radio-group)[data-variant='chip'] input:checked + label { … }                 /* 0,3,2 */
:is(ix-radio-group, .ix-radio-group)[data-variant='chip'][data-state='readonly'] input + label { … }   /* 0,3,2 */
```

### Dark mode

Temaet styres med CSS-klasser på rotelementet: `ix-light-mode` og `ix-dark-mode` tvinger henholdsvis lyst og mørkt tema. Klassen `ix-regard-color-scheme-preference` følger brukerens OS-preferanse via `prefers-color-scheme`.

:::warning Åpent spørsmål
Vurder om `ix-regard-color-scheme-preference` bør beholdes eller fjernes. Det er ønskelig at konsumenter eksplisitt velger tema (`ix-light-mode` / `ix-dark-mode`) fremfor å arve OS-preferanse automatisk.
:::

### Drivere for beslutningen

- Langsiktig holdbarhet — CSS fungerer uavhengig av React-versjoner og JS-trender
- Ingen runtime overhead — styling er statisk CSS
- Rammeverk-agnostisk — fungerer med React, Vue, Angular og ren HTML
- God caching og forutsigbar ytelse
- Enkel debugging med standard devtools

## Bakgrunn

Vi ønsker et designsystem som varer lenge uavhengig av JavaScript-trender, støtter eldre
nettlesere basert på `.browserslistrc`, og er enkelt å ta i bruk uten kompleks tooling.
Et designsystem bør fungere for alle konsumenter — ikke bare de som bruker React.

## Problemstilling

Hvilken styringstilnærming for styling sikrer at designsystemet er rammeverk-agnostisk,
langsiktig holdbart og uten runtime-overhead?

## Konsekvenser

### Hvem påvirkes?

Alle konsumenter av designsystemet — både React-konsumenter og team som kun bruker CSS.

### Ulemper

- Ingen automatisk scoping — `ix-`-prefix er eneste beskyttelse mot navnekollisjoner
- Ingen compile-time type checking av klassenavn
- Utility-klasser dekker ikke alle behov (men dette er bevisst — 80/20-regelen)
- Uten `:where()` må gruppetilstander skrives med full grunnform (`input + label`, ikke bare `label`), og presedensen mellom tilstander hviler på rekkefølgen i fila

### Tiltak mot ulemper

- `ix-`-prefix forhindrer navnekollisjoner i praksis
- TypeScript-typer for komponent-props gir type safety der det er mulig

## Forkastede alternativer

### `:where()` rundt hele komponentselektoren

Var praksis fram til 2026-10. Spesifisitet `0,0,0` taper mot enhver elementregel hos verten, som `a {}`, `h2 {}` og `table {}`. Det måtte lappes i Docusaurus, og rekkefølgen mellom filene ble avgjørende.

### `:where()` rundt indre deler

Foreslått i [indeks#291](https://github.com/SpareBank1/indeks/pull/291): ankeret skrives rett fram, og indre deler pakkes i `:where()`. Det løser `0,0,0`, men beholder to hooks for samme del (`label` og `.ix-checkbox__label`) og trenger `:where()` for at de skal veie like mye.

### Fjerne BEM helt

Deler kunne fått `data-field` i stedet for BEM-klasser. Forkastet fordi BEM er den eneste hooken for delene i tolv sammensatte komponenter, web componentene bruker BEM-klassene som runtime-hooks, og konsumentene bruker dem i over hundre kall. `data-field` treffer også deler i nøstede komponenter, noe `.ix-x__del` aldri gjør.

### Tailwind CSS

Et utility-first CSS-rammeverk som genererer kun de klassene som er i bruk. Svært
populært og brukes av mange designsystemer.

**Forkastet fordi:**
- Tailwind forutsetter at konsumenter bruker Tailwinds egen build-pipeline — et eksternt
  designsystem bør ikke kreve dette av sine konsumenter
- Tailwinds klassemodell og vårt token-system er grunnleggende ulike paradigmer som
  er vanskelig å kombinere uten å tape fordelene med begge

Beslutningen gjelder hvordan Indeks selv er stylet, ikke hva konsumenter kan bruke. Team som
allerede har Tailwind får en generert temafil som kobler Tailwinds navnerom til
`--ix-`-variablene, slik at de kan bruke tokenene våre uten å skrive `var()` overalt. Den
er valgfri og påvirker ikke CSS-en vi leverer. Se [Tailwind](../grunnleggende/tokens/tailwind).

### CSS-in-JS (styled-components, Emotion, vanilla-extract)

Styling defineres i JavaScript/TypeScript, nær komponentkoden.

**Forkastet fordi:**
- Runtime overhead (styled-components/Emotion genererer CSS i nettleseren)
- Binder designsystemet til React
- Kompliserer SSR
- Gjør CSS-only-bruk umulig

### CSS Modules

Modulbasert CSS der klassenavn scopet automatisk per komponent ved build.

**Forkastet fordi:** Genererte hash-baserte klassenavn er vanskelig å debugge og umulige å dokumentere
(klassenavnet `ix-button` er meningsfullt; `_button_a3f2c_1` er det ikke).
Eksponerer ikke stabile klassenavn som konsumenter kan bruke direkte.

### Sass/Less

CSS-preprocessorer med variabler, nesting og mixins.

**Forkastet fordi:** Moderne CSS har nå de fleste features som motiverte Sass (custom properties,
nesting, container queries). Et ekstra byggesteg gir kompleksitet uten tilsvarende verdi.
